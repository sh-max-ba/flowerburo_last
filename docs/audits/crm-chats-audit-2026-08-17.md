## 0. Вердикт коротко

- **Чаты сейчас не работают вовсе: API-ключ Wazzup недействителен** (`401 INVALID_APIKEY`). Тишина с 10.06 — это не баг кода, а мёртвый ключ/аккаунт. Перед подключением клиента ключ надо перевыпустить и пройти чек-лист из §2.

## 2. Чек-лист подключения клиента

1. В ЛК Wazzup получить **новый API-ключ** → `/settings` → вставить → «Проверить API key».
2. **CRM key не перегенерировать без нужды.** Кнопка «Сгенерировать новый» молча перезаписывает ключ, а в Wazzup остаётся зарегистрирован URL со старым `?key=` → все вебхуки начнут получать 401 **без какой-либо индикации в UI** (см. W-3, W-4). После любой смены ключа — сразу «Подключить webhook в Wazzup» и «Проверить подписки» (URI должен быть с `?key=`, подписки messagesAndStatuses + contactsAndDealsCreation).
3. Подключить канал(ы) WhatsApp клиента в ЛК → «Проверить каналы» в `/settings`.
4. Прогнать полный синк (пользователи → воронки → контакты → сделки) — сейчас `wazzup_user_sync`/`wazzup_pipeline_sync` пустые; без загруженных воронок и сотрудников Wazzup не шлёт createContact/createDeal и не маршрутизирует новых клиентов.
5. Сквозной тест: написать с личного телефона на номер магазина → должна появиться сделка «Заявка WhatsApp» в «Новая», бейдж у «Сделки», ответ из карточки сделки должен дойти; проверить голосовое + расшифровку.
6. Учесть находку C-3: бейдж/автообновление видят **только** `source='whatsapp'` — заявки из групп WhatsApp, Telegram, Instagram придут «молча».
7. Решить судьбу групповых чатов (W-5): каждая группа, где состоит номер магазина, будет плодить «клиента» + сделку «Заявка whatsgroup» (на проде уже есть 2 такие).

## 3. Находки: CRM

- **[CRITICAL] C-1. Срок сделки уезжает на −6 ч при каждом цикле «открыл → автосейв»** — `src/components/deals/deal-detail-page.tsx:2351` (локальная `toDatetimeLocal` = `new Date(value).toISOString()`), используется в префилле черновика (`:2118`) и уходит на сервер при каждом автосохранении любого поля (`:2199`). Для наивного `due_at` («время магазина», см. конвенцию и готовый правильный хелпер в `src/lib/datetime.ts:1-22`) на устройстве в поясе Бишкека 14:00 превращается в 08:00, и сдвиг накапливается; заражает и префилл срока заказа из сделки (`:2129`). Пока не стреляло только потому, что у всех сделок срок пуст. Подтверждено чтением кода.
- **[HIGH] C-2. Текстовый поиск клиентов показывает всех** — `src/lib/crm.ts:166-172`: для запроса без цифр `phone = '%%'`, условие `OR normalized_phone LIKE '%%'` матчит всех клиентов с телефоном (живая проверка: «Иван» → 118 из 119). UX: «поиск не работает».
- **[HIGH] C-3. Счётчик входящих видит только `source='whatsapp'`** — `src/app/api/deals/incoming-count/route.ts:34` и `src/lib/db/queries/owner-dashboard.ts:231`. Вебхук пишет `source = chatType` (whatsgroup/telegram/instagram…), такие заявки не попадают ни в бейдж, ни в триггер автообновления канбана (`deals-auto-refresh.tsx` реагирует только на этот счётчик), ни в плитку дашборда. На проде уже есть 2 сделки-whatsgroup мимо счётчика.
- **[HIGH] C-4. Нет индексов `orders(customer_id)`, `sales(customer_id)`, `orders(deal_id)`** — `listCustomers` (тройной LEFT JOIN, `crm.ts:175-190`) на живой БД строит `AUTOMATIC COVERING INDEX` на каждый вызов (каждый рендер `/clients`, `/deals`, `/deals/[id]`). Деградирует линейно с ростом продаж (сейчас 1270 строк — миллисекунды, но растёт быстрее всех).
- **[MEDIUM] C-5.** Канбан грузит **все** сделки без лимита и архива, включая закрытые (`crm.ts:398`, `deals-kanban.tsx`) — через полгода живой работы это тысячи DOM-карточек и толстый payload на каждый refresh.

- **[MEDIUM] C-8.** Выдача/самовывоз заказа не двигает сделку (`order-lifecycle.ts:890-930`) — выполненные сделки навсегда копятся открытыми в «Оформлен заказ», закрывать руками.

## 4. Находки: Wazzup

- **[HIGH] W-1 = C-3** (счётчик только whatsapp) — главный операционный риск при подключении TG/IG/групп.
- **[MEDIUM] W-2.** Редактирование/удаление сообщений клиентом не отражается: повторный `messageId` с `isEdited`/`isDeleted` отсекается `INSERT OR IGNORE` (`wazzup-webhook.ts:261-292`) — в чате остаётся старый текст, удалённое выглядит живым.
- **[MEDIUM] W-3.** Отклонённые по ключу вебхуки невидимы владельцу: роут отвечает 401 **до** записи в БД, а плитка «Ошибки авторизации» (`wazzup.ts:1508`) и алерт (`settings-page.tsx:1222`) ищут строки `error LIKE 'unauthorized webhook:%'`, которые код никогда не создаёт. Если ключ в URL разъедется с crmKey — входящие тихо теряются при «здоровой» панели (следы только в journald).
- **[MEDIUM] W-4.** «Сгенерировать новый» CRM key перезаписывает ключ без предупреждения и без переподключения вебхука (`settings-page.tsx:880`, `wazzup.ts:317`) — в связке с W-3 это тихая потеря всех входящих.
- **[MEDIUM] W-5.** Входящие из групп WhatsApp создают клиентов и сделки наравне с личными чатами (`wazzup-webhook.ts:299,406`); подписи «Заявка whatsgroup» нет в словаре labels. Шум на проде уже есть.
- **[MEDIUM] W-6.** Из статус-вебхука `status:'error'` отбрасывается объект причины (`SPAM`, `24_HOURS_EXCEEDED`, `CHANNEL_REJECTED`…) — менеджер видит красную иконку без объяснения (`wazzup-webhook.ts:316-336`).
- **[LOW]** Тест-пинг `{test:true}` проверяется ПОСЛЕ авторизации (fail-closed осознанно) → регистрация «голого» URL без `?key=` упадёт с `testPostNotPassed`, а кнопка подключения не гейтится на пустой crmKey; null-фолбэк handshake createContact/createDeal отвечает `{ok}` вместо сущности (связка не встанет, повторного вебхука не будет); `channelsUpdates:false` — падение канала (qr/notEnoughMoney/blocked) CRM не заметит; phone_fallback всегда «первый активный whatsapp-канал» (при 2+ номерах все новые диалоги с первого; без WhatsApp-канала — вводящая в заблуждение ошибка); двойной сабмит текста возможен при удержанном Enter (crmMessageId уникален на вызов); голосовые копятся в `public/uploads/voice/` без ротации, как и `raw_payload` событий; «SSRF-guard» в `media-fetch.ts` — только проверка протокола; плитка «Webhook auth: Гибкий» и «Проверить webhook endpoint» вводят в заблуждение (флаг вестигиальный, проверка локальная).

## 5. Что работает правильно (проверено)

Авторизация вебхука fail-closed с timing-safe сравнением (живой тест: 401, БД не тронута); сырой payload + дедуп по sha256 и `message_id UNIQUE`; переобработка failed-событий без потери сообщений; ответ телом CRUD-сущности на createContact/createDeal; обратный синк после ответа через `after()`; `crmMessageId` на каждой отправке, `REPEATED_CRM_MESSAGE_ID` = успех; ретраи с Retry-After на 429/5xx; батчи ≤100; секреты только на сервере, в клиент уходят маски; все эндпоинты чатов под сессией, медиа — через серверный прокси по id; транзакции на всех мутациях CRM; `pricing.ts` един для сервера и UI; гарды сделка↔заказ (заморозка итогов, блок позиций, перенос предоплат, зеркалирование оплат/возвратов) продуманы; поллинг аккуратный (AbortController, пауза при скрытой вкладке/диалоге/DnD); `smoke:wazzup` полностью песочница (temp-БД + мок fetch), прод не трогает.
