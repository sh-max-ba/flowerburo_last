# План улучшения UI/UX FlowerOps

## 1. Резюме (Executive summary)

FlowerOps — это работающая, функционально полная CRM/бэк-офис для цветочного магазина, построенная на крепком техническом фундаменте: чистые примитивы shadcn/base-ui, продуманный складской документооборот (предпросмотр-перед-применением, черновик/проведение, блокировка проведённых актов), корректная централизованная денежная математика (`src/lib/pricing.ts`) и хорошая сверка кассы («Формула кассы»). Средний балл по девяти модулям — **5,4 из 10**: ни один модуль не «сломан», но почти каждый теряет в скорости, приоритизации и предсказуемости именно там, где это критично для ежедневной работы у прилавка под таймпрессингом.

Главная системная проблема — **разрыв между заявленной дизайн-системой и реальностью**. Тема в `globals.css` полностью монохромна (oklch chroma=0, единственный цвет — красный `--destructive`), но статусы в цветочном магазине («Готов», «Передан курьеру», «Просрочено», «оплачен», «недостача», «мало на складе») требуют считываемости с одного взгляда. В результате 14 модулей в обход системы хардкодят tailwind-цвета (47 вхождений `bg-emerald/amber/red/...`) — это «монохром плюс нескоординированный ad-hoc цвет», худший из обоих миров: нет единого источника правды, дрейф гарантирован, на соседних экранах один и тот же статус выглядит по-разному. Параллельно тема наполовину не достроена: полный блок `.dark` и `dark:`-варианты существуют, но `ThemeProvider` нет нигде, поэтому тёмная тема — мёртвый код, а `sonner` через `useTheme()` без провайдера молча следует за темой ОС.

**Вывод: нужен не полный редизайн, а сфокусированный рефакторинг дизайн-системы плюс точечные переделки 3–4 ключевых экранов.** Архитектура оболочки (сайдбар + топбар + CrmShell) звуковая. Но прежде чем чинить отдельные модули, нужно ввести минимальный набор семантических токенов и Badge-вариантов, решить судьбу тёмной темы, и стандартизировать состояния (loading/empty/error) и паттерны форм. Это снимает корневую причину половины находок. Поверх — два настоящих P0-дефекта (drag сделок не сохраняется; нет расчёта сдачи на кассе) и набор находок про необратимые действия без подтверждения, приоритизацию по сроку и отзывчивость на планшете.

## 2. Сквозные проблемы (cross-cutting themes)

### 2.1. Монохромная палитра убивает читаемость статусов (самая частая проблема)
**Где:** дизайн-система (`globals.css:51-84`, `badge.tsx:10-22`), Касса (`cash-page.tsx:165,474,868,1130,1144`), Стол/Готовые заказы (`ready-orders-page.tsx:82,176-192`, `order-shared.tsx:575-585`), Сделки (`deal-detail-page.tsx:853,1256-1277,1446-1517,1919-1932`, `deals-kanban.tsx:570`), Клиенты (`customers-page.tsx:77,109,116`), Букеты (`bouquets-page.tsx:537-540,570-582`), Склад (`stock/acts/page.tsx:165-191`, `imports/[id]/page.tsx:144-154`), Смены (`shift-pages.tsx:648-654`, `shift-sheet.tsx:210-215`), Настройки (`settings-page.tsx:436,925-935`).
**Почему важно:** статус — главный сигнал в каждом модуле, и сейчас он либо невидим (серый secondary ≈ серый outline: «осталось 2» выглядит как «осталось 200», «смена открыта» как «закрыта», «недостача 5000» как «излишек 1»), либо нарисован ad-hoc цветом, который ломается при смене палитры и расходится между экранами.
**Направление решения:** ввести малый набор семантических low-chroma токенов (success/warning/info) + Badge-варианты, мигрировать все 47 хардкодов на них. Где цвет недостаточен в сером — дублировать сигнал **формой**: иконка (lucide уже импортирован) + текстовая метка, а не только оттенок. Это раздел 3.

### 2.2. Необратимые действия без подтверждения и без визуальной иерархии
**Где:** Касса — «Изъятие наличных» один кликом (`cash-page.tsx:617-626,1168-1224`); Стол заказов — «Букет готов» (необратимое списание склада) равновесна «В работу» и без confirm, «Отменить» — деструктив без alert (`orders-page.tsx:144-159`); Сделки — удаление позиции/группы состава без подтверждения (`deal-detail-page.tsx:1093-1102,1197-1206`); Склад — списание в минус разрешено без подтверждения (`stock-document-form.tsx:272-312`); Смены — «Закрыть смену» (финализирует кассу) без confirm (`shift-sheet.tsx:335-339`); Букеты — «Выключить» виднее, чем «Изменить», без confirm (`bouquets-page.tsx:550-559`). Корень: `AlertDialogAction` по умолчанию рендерится как обычная (чёрная) primary-кнопка, без destructive-акцента (`alert-dialog.tsx:144-155`).
**Почему важно:** это деньги и пересборки. Опечатка в количестве (лишний ноль) или промах мимо кнопки необратимы.
**Направление:** обернуть необратимые операции в `AlertDialog` (примитив уже есть), сделать деструктивную кнопку `variant="destructive"` по умолчанию в опасных контекстах, выстроить иерархию кнопок (главное действие по статусу — primary, второстепенные — outline/ghost/в dropdown).

### 2.3. Отсутствие/слабость состояний loading, empty и «ничего не найдено»
**Где:** нет route-transition фидбэка при навигации (`crm-shell.tsx:121-129`); `Empty`-примитив без видимой рамки (`ui/empty.tsx:5-16`); пустой стол заказов не отличает «нет заказов» от «нет смены» (`orders-page.tsx:70-76`); склад показывает «Склад пуст» даже когда просто фильтр ничего не нашёл (`stock-page.tsx:506-508`); канбан сделок без board-level empty (`deals-kanban.tsx:204-296`). Общий шаблон pending — один `useTransition` на всю страницу, блокирующий все кнопки сразу без точечного спиннера (orders, ready-orders, deals, users, settings).
**Почему важно:** на счётчике под нагрузкой «всё посерело» читается как «зависло», провоцирует двойные клики; пустой серый экран — как ошибка загрузки.
**Направление:** добавить `loading.tsx`/скелетоны на динамические маршруты, починить рамку `Empty` и завести конвенцию «иконка + действие», различать пустоту от фильтра, ввести per-row/per-button pending (хранить id обрабатываемого элемента).

### 2.4. Непоследовательные паттерны форм: сырые `<select>`, нет inline-валидации, мелкие тач-цели
**Где:** сырой `<select>` вместо shadcn `Select` — Касса (способ оплаты, тип скидки: `cash-page.tsx:499-534,1071-1101`), Готовые заказы (формы доплаты: `ready-orders-page.tsx:244-256,338-349`); inline-валидация почти не используется вне логина (`field.tsx:176-225`, ошибки приходят только тостом) — Клиенты, Сделки, Смены, Пользователи; тач-цели <44px (steppers/delete `size-7` в `product-line-items.tsx:219-250`, `<select className="h-8">`); нет `inputMode`/маски на телефон и деньги (`input.tsx`, телефоны как plain text везде); `Calendar`-примитив собран, но не используется нигде — все даты через сырой `<input type="date">` без русской локали (`calendar.tsx` + 6 вхождений в 5 модулях).
**Почему важно:** способ оплаты выбирается на каждой продаже; ошибки-тостом исчезают и заставляют переотправлять; на планшете 28–32px и буквенная клавиатура на телефоне тормозят.
**Направление:** свапнуть все `<select>` на `Select`; завести общие `MoneyInput`/`NumberInput`/`PhoneInput` (`InputGroup` + `inputMode`); собрать `DatePicker` (`Popover` + `Calendar` + `locale=ru`) один раз и заменить нативные; протянуть field-level ошибки из server actions в `FieldError`+`aria-invalid`.

### 2.5. Перегруженные карточки и плоские «стены» без иерархии
**Где:** карточка готового заказа — 3 блока цифр, действие тонет внизу (`ready-orders-page.tsx:195-275`); деталь смены — 15 одинаковых stat-карточек, ключевая «Разница» = карточка №15 (`shift-pages.tsx:121-137`); карточка сделки — монолит на 2171 строку, денежные действия спрятаны в табе «Оплата» (`deal-detail-page.tsx`); вкладка Wazzup в настройках — 430 строк, 7 карточек подряд с дублирующимися контролами (`settings-page.tsx:427-855`); карточка клиента — always-open форма редактирования вместо read-first + дублированные блоки (`customer-detail-page.tsx:63-75`); тулбар склада — 7 равновесных кнопок (`stock-page.tsx:457-502`).
**Почему важно:** самое важное (что отдать клиенту, сошлась ли касса, продвинуть этап, принять оплату) не самое заметное; пользователь сканирует шум.
**Направление:** прогрессивное раскрытие (Collapsible/«Подробнее»), вынос главного действия в закреплённую зону, сведение второстепенного в DropdownMenu/вложенные Tabs, read-first с редактированием по кнопке.

### 2.6. Таблицы переполняются на планшете без адаптива
**Где:** базовый `Table` — `overflow-x-auto` + `whitespace-nowrap` без sticky-header и без card-fallback (`ui/table.tsx:7-19`); конкретно: корзина кассы `min-w-[900px]` (`product-line-items.tsx:96-110`), список клиентов `min-w-[900px]`/8 колонок (`customers-page.tsx:87`), каталог букетов `min-w-[960px]` (`bouquets-page.tsx:498`), состав сделки `min-w-[620px]` в узком рейле (`deal-detail-page.tsx:1029`), список актов 11 колонок и детали импорта 13 колонок (`stock/acts/page.tsx:113-158`, `imports/[id]/page.tsx:60-105`), история смен без лимита/пагинации (`shift-pages.tsx:39-104`).
**Почему важно:** планшет у прилавка — заявленный сценарий; двухосевой скролл и «уезжающее» за край действие тормозят и провоцируют слепые тапы.
**Направление:** ниже `md` — карточный fallback (паттерн в коде есть, `ResponsiveTable` в stock-page); иначе минимум sticky `thead` + `active:bg` для тач-фидбэка; скрывать второстепенные колонки `hidden lg:table-cell`.

### 2.7. Хардкод `zinc-*`/`white` в обход токенов
**Где:** `page-header.tsx:21-23`, `ui/table.tsx:11,26,73,86`, `ui/card.tsx:15,41,53`, `ui/sidebar.tsx:447,522,636`, `login-form.tsx:25`, `access-denied.tsx:14-15`.
**Почему важно:** токены перестают быть источником правды; смена палитры/контраста/тёмная тема не распространяется.
**Направление:** заменить на `text-foreground`/`text-muted-foreground`/`border-border`/`bg-card`/`bg-muted`/`text-sidebar-foreground`. Делать вместе с решением по тёмной теме (3.6).

## 3. Предложение по дизайн-системе (design refactor)

Это фундамент: выполняется первым, потому что снимает корневую причину тем 2.1, 2.2, 2.3 и части 2.4/2.7.

### 3.1. Семантические токены (палитра)
Сейчас вся палитра — chroma=0. Добавляем **минимальный** набор low-chroma семантических токенов, чтобы серый «хром» остался спокойным, а статус получил единый координированный язык цвета. В `:root` блок `globals.css` (после строки ~84):

```css
:root {
  /* статус: low-chroma, читаемо в спокойном сером UI */
  --success: oklch(0.62 0.13 150);
  --success-foreground: oklch(0.98 0 0);
  --success-subtle: oklch(0.96 0.02 150);        /* фон бейджа */
  --success-subtle-foreground: oklch(0.40 0.10 150);

  --warning: oklch(0.80 0.12 85);
  --warning-foreground: oklch(0.27 0.05 85);
  --warning-subtle: oklch(0.96 0.04 85);
  --warning-subtle-foreground: oklch(0.45 0.09 85);

  --info: oklch(0.62 0.10 240);
  --info-foreground: oklch(0.98 0 0);
  --info-subtle: oklch(0.96 0.02 240);
  --info-subtle-foreground: oklch(0.42 0.08 240);

  /* --destructive уже есть; добавим subtle-пару для бейджей */
  --destructive-subtle: oklch(0.96 0.03 25);
  --destructive-subtle-foreground: oklch(0.45 0.13 25);

  /* акцент/бренд: один сдержанный фирменный оттенок (опц., для активного пункта nav, ссылок) */
  --accent-brand: oklch(0.55 0.08 350);           /* приглушённо-розовый — уместен для цветочного */
  --accent-brand-foreground: oklch(0.99 0 0);
}
```
И в блок `@theme` (рядом с существующими `--color-*`):
```css
@theme {
  --color-success: var(--success);
  --color-success-foreground: var(--success-foreground);
  --color-success-subtle: var(--success-subtle);
  --color-warning: var(--warning);
  --color-warning-foreground: var(--warning-foreground);
  --color-warning-subtle: var(--warning-subtle);
  --color-info: var(--info);
  --color-info-subtle: var(--info-subtle);
  /* ...и foreground-пары */
}
```
**Принцип:** цвет используется только для статуса/сигнала, не для «хрома». Хром остаётся серым. Контраст текста на subtle-фоне проверить на ≥4.5:1.

### 3.2. Badge-варианты статусов
В `ui/badge.tsx` (`cva` на строках 10-22) добавить варианты, использующие subtle-пары, и поддержать иконку-слот (`data-icon="inline-start"` Badge уже умеет):
```
success:     bg-success-subtle text-success-subtle-foreground
warning:     bg-warning-subtle text-warning-subtle-foreground
info:        bg-info-subtle text-info-subtle-foreground
destructive-subtle: bg-destructive-subtle text-destructive-subtle-foreground
```
Использование: `<Badge variant="success">Готов</Badge>`, `<Badge variant="warning"><AlertTriangleIcon/>Мало ≤3</Badge>`. **Везде** добавлять иконку, чтобы статус читался и без цвета. Затем мигрировать 47 ad-hoc вхождений (раздел 2.1) на эти варианты — это устраняет дрейф и делает статус единым между экранами (например, «Готов» на `/orders` и `/ready-orders` станет идентичным).

### 3.3. Паттерны статусов (общий компонент)
Завести компоненты-обёртки, чтобы статус был один и тот же во всех модулях:
- `OrderStatusBadge(status)` — единый для `/orders` и `/ready-orders` (заменяет `OrderBadge` и `ReadyStatusBadge`).
- `DifferenceBadge(diff)` — для смен: «Излишек {money}» (secondary) / «Недостача {money}» (destructive + `AlertTriangleIcon` при превышении порога) / «Совпало» (success). Применить в истории, детали и диалоге закрытия.
- `StockBadge(available)` — ≤3 → warning + иконка + bold; 0 → заметный контраст; <0 → destructive. Использовать `product.available` и единый порог из данных.
- `UrgencyBadge(dueAt)` — «Просрочено» (destructive) / «Сегодня» (warning) / «Через N ч» (outline). Переиспользовать существующую `orderUrgencyClass`.

### 3.4. Типографика
Сейчас 3 разных размера заголовка по поверхностям. Зафиксировать малую шкалу и применять единообразно:
- page-title: 24px / 600 / `font-heading` (Cal Sans);
- section-title (CardTitle): 16px / 600 / `font-heading`;
- body: 14px / 400.
Сделать заголовок `AppTopbar` (`app-topbar.tsx:44`) `font-heading` — сейчас самый заметный заголовок не в брендовом шрифте. Решить дублирование `PageHeader` и топбар-title (часто один и тот же текст).

### 3.5. Плотность/спейсинг и тач
- Тач-цели в корзине и формах: steppers/delete → `size="icon"` (40px) минимум `icon-lg` (36px).
- Базовый `Table`: добавить опцию sticky `thead` и `active:bg-muted` для тач-фидбэка; для data-heavy модулей — card-fallback ниже `md`.
- Контент-max-width 1600px, паддинги p-4/p-5 — оставить.

### 3.6. Тёмная тема — решить и зафиксировать
Тёмная тема — мёртвый код (полный `.dark` + `dark:`-варианты, но нет `ThemeProvider`; `sonner` через `useTheme()` без провайдера). **Рекомендация: удалить** (вариант B) как менее рискованный при выбранном монохромном направлении — убрать `.dark`-блок, `dark:`-варианты в примитивах, захардкодить `theme="light"` в `sonner.tsx`. Альтернатива (вариант A): по-настоящему подключить `next-themes` ThemeProvider + переключатель в футере сайдбара — тогда обязательна миграция хардкод-`zinc-*` на токены (2.7). В обоих случаях осознанно решить судьбу `richColors` у `<Toaster>` (`layout.tsx:34`): он сейчас красит success/error в зелёный/красный, противореча монохрому — либо убрать (тосты серые, различать иконкой `CircleCheck`/`OctagonX`), либо принять как часть семантического набора из 3.1.

### 3.7. Состояния
- `ui/empty.tsx:5-16` — добавить `border border-dashed border-border` (сейчас `border-dashed` без ширины = невидимо), завести конвенцию «EmptyMedia (иконка) + EmptyContent (кнопка действия)», поднять вес `EmptyTitle`.
- Завести `loading.tsx` со скелетонами (`Skeleton`/`SidebarMenuSkeleton` уже есть) на динамических маршрутах + route-transition индикатор в оболочке (`useLinkStatus` Next 16 или верхний прогресс-бар).
- `AlertDialogAction` (`alert-dialog.tsx:144-155`) — конвенция/проп `tone="danger"` → `variant="destructive"`, чтобы опасное подтверждение визуально отличалось от благонамеренного.

### 3.8. Таблицы vs карточки (правило)
Карточный grid — для каталогов и очередей, где важна узнаваемость/сканирование (Букеты, потенциально Стол заказов как kanban). Таблица — для плотного аудита (склад, история, акты), но с card-fallback ниже `md`. Не использовать широкую 8-колоночную таблицу для быстрых сценариев у прилавка (корзина кассы).

**Качественные критерии готовности дизайн-системы:**
- `grep` по `bg-emerald|bg-amber|bg-green|bg-red-|bg-yellow|bg-sky|bg-zinc-950|text-amber|border-emerald` в `src/components` возвращает **0** вне `globals.css`/`badge.tsx` (все 47 ad-hoc цветов мигрированы).
- Один и тот же статус («Готов», «Просрочено», «недостача») выглядит идентично на всех экранах.
- Каждый динамический маршрут имеет `loading.tsx`; ни один пустой экран не читается как ошибка (рамка + иконка + действие).
- Каждое необратимое действие (изъятие, готов, отмена, списание в минус, закрытие смены, удаление) проходит через `AlertDialog` с destructive-акцентом.
- `npm run build` (type-check gate) и Playwright-smoke зелёные; визуальный прогон на планшетной ширине без двухосевого скролла в основных сценариях.
