# Системный аудит FlowerOps

Дата: 2026-05-31
Область: весь проект (Next.js 16.2.6 / React 19 / better-sqlite3).
Метод: сквозная трассировка бизнес-потоков и чтение исходников по четырём направлениям — безопасность, корректность бизнес-логики, производительность, архитектура/качество кода. Ссылки даны как `файл:строка` на момент аудита (номера строк могут немного сдвигаться при правках — ориентируйтесь на имя функции).

Легенда серьёзности: **critical** — потеря денег/товара или компрометация системы; **high** — заметный риск или деградация; **medium** — важно, но терпит; **low** — гигиена/уборка.

---

## TL;DR — порядок работ

**P0 — сделать первым (безопасность + прямые денежные потери):**
- `SEC-1` Дефолтный секрет подписи сессий → подделка cookie любого пользователя (полная компрометация).
- `BL-1` Отмена уже собранного заказа теряет товар и деньги (нет возврата, нет восстановления склада).
- `BL-2` Возврат наличных (`cash_refund`) нигде не создаётся — вернуть деньги физически нечем.
- `SEC-2`/`SEC-3` Wazzup webhook пишет в БД до проверки авторизации и по умолчанию открыт.

**P1 — высокий приоритет (производительность + целостность данных):**
- `PERF-1` `getShiftShellContext` тянет полный `getDashboardData()` на 8 страницах.
- `PERF-2` 5-секундный `router.refresh()` пересчитывает весь тяжёлый рендер.
- `PERF-3` `shiftDetails` строятся для всех 20 смен; `calculateShiftSummary` считается трижды на смену.
- `PERF-4` Отсутствуют индексы на горячих FK/фильтрах.
- `BL-3` Нет проверки доступного остатка → перепродажа и отрицательный сток.
- `BL-4` Импорт склада перезаписывает абсолютные `stock`/`reserved` (TOCTOU + ломает резерв).
- `SEC-4` `secure`-cookie выключен даже в продакшене (трафик по HTTP).

**P2 — средний приоритет / рефакторинг (поддерживаемость):**
- `ARCH-1` Монолит `backoffice.tsx` (~5700 строк) + сериализация всего `DashboardData` в клиент.
- `ARCH-2` Матрица ролей продублирована в 4–5 местах (уже разъехалась).
- `ARCH-3` Дублирующиеся мапперы db.ts ↔ crm.ts с расхождением нормализации статуса.
- `ARCH-4`/`ARCH-5` Нет версионирования схемы; `zod` установлен, но не используется.
- `PERF-5`/`ARCH-6` `revalidatePath` веером по 9 путям на каждую мутацию.
- Уборка мёртвого кода и дубликатов лейблов.

## 1. Безопасность

### SEC-1 — Дефолтный секрет подписи сессий (полная компрометация) — critical
- **Где:** `src/lib/auth.ts:140-142` (`getSessionSecret`), используется в `signSessionPayload` и формате токена `auth.ts:104-111`.
- **Проблема:** `AUTH_SECRET || NEXTAUTH_SECRET || "flower-ops-local-session-secret"`. В `.env`/`.env.example` секрет не задан, то есть боевой ключ подписи — это публичная константа из репозитория. Токен `v2.<userId>.<expiresMs>.<nonce>.<HMAC>` проверяется только пересчётом HMAC.
- **Эксплойт:** зная константу, можно офлайн сгенерировать валидный cookie `flower_ops_session` для `userId=1` (обычно владелец) и получить полный доступ. Подписанный путь даже не обращается к таблице `sessions`.
- **Фикс:** сделать секрет обязательным — падать на старте, если `AUTH_SECRET` не задан или короткий; убрать fallback. Сгенерировать сильный секрет в `.env`, добавить переменную в `.env.example`. Ротация секрета инвалидирует все старые токены (приемлемо).

### SEC-2 — Webhook пишет в БД до проверки авторизации — high
- **Где:** `src/app/api/wazzup/webhook/route.ts:27` (`saveWazzupWebhookEvent`) выполняется **раньше** `isWazzupWebhookAuthorized` (`:28`) и до отказа `401` (`:49`).
- **Проблема:** сырой body любого неавторизованного POST пишется в `wazzup_webhook_events.raw_payload` ещё до auth-гейта; нет ограничения размера тела и rate-limit.
- **Эксплойт:** зная публичный URL, атакующий заваливает таблицу событий произвольным JSON (disk-fill / DoS, замусоривание). Идемпотентность по `event_hash` не спасает — payload легко варьировать.
- **Фикс:** сначала авторизация → `401`, и только потом запись. Ограничить размер тела; ввести ротацию/лимит таблицы событий.

### SEC-3 — Webhook фактически открыт по умолчанию — high
- **Где:** `src/lib/wazzup-webhook.ts:45-91` (`isWazzupWebhookAuthorized`); дефолты `wazzup.ts:222`, `:259`.
- **Проблема:** при пустом `crmKey` функция возвращает `authorized:true` (только warning). И даже при заданном ключе, если `webhookAuthRequired=0` (дефолт), принимается любой POST.
- **Эксплойт:** без ключа можно инъектить `createContact`/`createDeal`/`messages` → создавать клиентов, открывать сделки, переназначать ответственного, подсовывать «сообщения» в чаты (`processWazzupWebhook`).
- **Фикс:** отсутствие CRM key = **deny**, не allow. `webhookAuthRequired` по умолчанию `true`. Сравнение ключа — константное по времени.

### SEC-4 — `secure`-cookie выключен даже в продакшене — high
- **Где:** `src/lib/auth.ts:41,144-151` (`shouldUseSecureSessionCookie` всегда `false`, если нет явного override); цель деплоя — `http://91.99.4.32:3000` (`wazzup.ts:211`).
- **Проблема:** при `sameSite:"lax"` сессионная cookie ходит по открытому HTTP.
- **Эксплойт:** перехват cookie на канале (офисный Wi-Fi/LAN/ISP) → реплей до 7 дней. `httpOnly` стоит, но это не защищает от сниффинга сети.
- **Фикс:** `secure=true` при `NODE_ENV==="production"` (опт-аут только для локалки); терминировать TLS, отдавать по HTTPS.

### SEC-5 — Полный `wazzupStatus` уходит всем ролям, включая флориста — medium
- **Где:** `src/components/backoffice-route.tsx:32` (`wazzupStatus={getWazzupSettingsStatus()}` безусловно); сборка в `wazzup.ts:228-249`.
- **Проблема:** webhook URL, маскированные ключи, диагностика и статусы синка пользователей сериализуются в клиент для всех, хотя раздел настроек — только owner. (Сами `apiKey`/`crmKey` не утекают — только `maskSecret()`.)
- **Фикс:** передавать `wazzupStatus` только при `user.role === "owner"`; считать лениво в ветке настроек.

### SEC-6 — Нет защиты от перебора на логине — medium
- **Где:** `src/app/auth-actions.ts:10-24`, `src/lib/auth.ts:81-90`. bcrypt cost 12 (`password.ts:3`) лишь замедляет.
- **Фикс:** rate-limit по IP/логину + временная блокировка/бэкофф после серии неудач.

### SEC-7 — CRM key в query-параметре (`?key=`) утекает в логи — medium
- **Где:** `route.ts:30` принимает `?key=`/`?crmKey=`; URL строится с ключом в query (`wazzup.ts:2226-2239`, `getSecureWazzupWebhookUrlForOwner`).
- **Фикс:** предпочитать заголовок `Authorization: Bearer` (уже поддержан, `wazzup-webhook.ts:64`); отключить логирование query на этом маршруте у реверс-прокси; ротировать ключ при подозрении.

### SEC-8 — Подписанный токен не отзывается до истечения — low
- **Где:** `src/lib/auth.ts:55-58`. Подписанный путь проверяет только HMAC+expiry и не сверяется с `sessions`, поэтому `logout()`/деактивация пользователя не инвалидируют выданный токен до 7 дней.
- **Фикс:** сократить TTL, либо в подписанном пути дополнительно проверять наличие токена в `sessions` и `is_active`.

> **Проверено и ОК (не требует действий):** `.env` не закоммичен (в индексе только `.env.example` с пустыми ключами); `WAZZUP_API_KEY` уходит только server-to-server в `Authorization`-заголовке, не в клиент; iframe-URL — это транзиентный токен Wazzup, не наш ключ; **SQL-инъекций нет** (динамические фрагменты используют только внутренние литералы, значения биндятся параметрами; `PRAGMA table_info(${table})` вызывается только с константами); загрузка картинок хорошо защищена (allow-list типов+расширений, лимит 5 МБ, имя файла генерится сервером, `flag:"wx"`, нет SVG, защита от path-traversal); все `route.ts` и server actions проверяют `requireUser`/`requireRole`; идемпотентность webhook по SHA-256 `event_hash` + `INSERT OR IGNORE` корректна.

## 2. Бизнес-логика (корректность)

### BL-1 — Отмена уже собранного заказа теряет товар и деньги — critical
- **Где:** `src/lib/db.ts:5660-5698` (`cancelOrder`), обработка в `src/app/actions.ts:818-832`.
- **Проблема:** при статусе `Готов`/`Передан курьеру` функция только ставит `alreadyBuilt=true` и переводит заказ в `Отменен`. Склад (списанный в `markOrderReady`) **не** восстанавливается, `cash_refund` **не** создаётся, `paid`/`prepaid` остаются на заказе. Для `Передан курьеру` к тому же мог быть выплачен курьерский payout из кассы.
- **Последствие:** деньги клиента числятся полученными (искажают `expectedCash`), товар «уехал» без сторно. Единственный эффект — тост «склад автоматически не восстанавливается».
- **Фикс:** при отмене оплаченного заказа — записать `cash_refund` на сумму `paid`/`prepaid` в открытую смену и обнулить их; для собранных заказов — либо сторнирующее движение склада (`order_fulfill`-reverse), либо обязательный ручной акт возврата. Не оставлять списанным молча.

### BL-2 — Возврат наличных (`cash_refund`) нигде не создаётся — critical
- **Где:** тип определён `db.ts:24,514`, суммируется в `calculateShiftSummary` (`db.ts:2098`) и `getShiftDetails` (`db.ts:2255`), есть лейбл (`labels.ts:37`) и отображение (`shift-pages.tsx:661`) — но **ни одного производителя** транзакции этого типа нет (подтверждено grep).
- **Последствие:** формула `expectedCash` вычитает величину, которая всегда ноль; вернуть деньги клиенту невозможно. Прямо блокирует корректный фикс `BL-1`.
- **Фикс:** добавить action возврата (на отмене заказа/сделки и ручная кнопка возврата), вызывающий `recordCashTransaction(..., type:"cash_refund", ...)`.

### BL-3 — Нет проверки доступного остатка → перепродажа и отрицательный сток — high
- **Где:** `applyProductDelta` `src/lib/db.ts:2911-2922` (пишет `afterStock`/`afterReserved` без нижней границы); вызовы: `createOrder` (`:4959`), `createOrderFromDeal` (`:5184`), `markOrderReady`/`fulfillOrderItems` (`:5378`), `createSale` (`:4574`), `adjustProductStock` "out" (`:4069`), `postStockDocument` `stock_out` (`:4287`).
- **Проблема:** резерв/продажа/списание не проверяют `available >= qty` / `stock >= qty`; `available` и `reserved` могут уйти в минус.
- **Фикс:** добавить проверку доступности в соответствующих транзакциях (резерв/продажа — по `available`, списание/`stock_out` — по `stock`), либо явный флаг «разрешить минус». В `applyProductDelta` — `afterReserved = Math.max(0, …)`.

### BL-4 — Импорт склада перезаписывает абсолютные `stock`/`reserved` — high
- **Где:** preview `db.ts:3685-3732`; apply `db.ts:3457-3520` (`applyWarehouseImport`).
- **Проблема:** (а) apply пишет `stock = newStock` (абсолют, посчитанный на момент preview) — продажи/резервы между preview и apply молча затираются (реальный кросс-запросный TOCTOU). (б) если в файле есть колонка `reserved`, перезаписывается живой резерв, поддерживаемый жизненным циклом заказов → ломается `available = stock - reserved`. Нет ревалидации `oldStock` на момент apply.
- **Фикс:** на apply перечитывать текущий остаток и применять **дельту**, а не абсолют (или отклонять, если значение изменилось с момента preview). `reserved` импортом не трогать (или пересчитывать из активных заказов).

### BL-5 — `deleteProduct` удаляет товар, на который ссылаются заказы / есть резерв — high
- **Где:** `db.ts:4006-4039`; у `order_items.product_code` нет FK (`db.ts:768-784`), у `sale_items.product_code` — есть RESTRICT FK (`db.ts:586`).
- **Проблема:** удаление без проверки `reserved>0` и ссылок из `order_items`/`deal_items`. Активный заказ осиротеет, а попытка собрать/отменить его кинет `Товар … не найден` из `applyProductDelta`. Удаление когда-либо проданного товара бросит сырую ошибку FK вместо понятного сообщения.
