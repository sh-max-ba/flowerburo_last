# Чеклист деплоя FlowerOps

Живой документ. Сюда складываются обязательные шаги при выкатке, которые появляются по мере выполнения [плана аудита](SYSTEM_AUDIT.md). Перед каждым деплоем — пройтись сверху вниз.

Легенда: ⬜ не сделано · ✅ сделано на текущем сервере.

---

## После фазы P0 (безопасность + деньги) — ОБЯЗАТЕЛЬНО

Эти три шага закрывают изменения P0. Если их не сделать, сломается то, что раньше «работало» (вход и приём webhook).

### 1. ⬜ Задать `AUTH_SECRET` (иначе вход в production упадёт)
- Сгенерировать секрет:
  ```bash
  openssl rand -base64 48
  ```
- Прописать в `.env` (рядом с `app.db`, не коммитить):
  ```bash
  AUTH_SECRET=<сгенерированное_значение>
  ```
- Требование: непустой и **не короче 32 символов**, иначе при логине будет ошибка (по дизайну, см. `SEC-1`).
- ⚠️ Смена секрета инвалидирует все активные сессии — все пользователи будут разлогинены. Это нормально, делать в окно простоя.
- Где проверяется: [src/lib/auth.ts](../../src/lib/auth.ts) → `getSessionSecret`.

### 2. ⬜ Настроить `SESSION_COOKIE_SECURE` под протокол сервера
- Если сервер отдаётся по **HTTPS** — ничего не делать (по умолчанию `secure=true` в production). Рекомендуется.
- Если сервер отдаётся по **простому HTTP** (как сейчас `http://91.99.4.32:3000`) — обязательно:
  ```bash
  SESSION_COOKIE_SECURE=false
  ```
  Иначе cookie не отправится по HTTP и вход не пройдёт.
- Правильное долгосрочное решение — поднять TLS/HTTPS и убрать этот опт-аут.
- Где проверяется: [src/lib/auth.ts](../../src/lib/auth.ts) → `shouldUseSecureSessionCookie`.

### 3. ⬜ Сгенерировать CRM key и переподключить Wazzup webhook
- Зайти в CRM: `/settings → Wazzup`.
- Сгенерировать CRM key, скопировать защищённый Webhook URL, переподключить webhook (включить `messagesAndStatuses` и `contactsAndDealsCreation`).
- ⚠️ Без CRM key входящие webhooks теперь **отклоняются** (`401`) — раньше принимались открыто (это и была дыра `SEC-2`/`SEC-3`). Пока ключ не задан, заявки из WhatsApp/Instagram приходить не будут.
- Предпочтительно использовать заголовок `Authorization: Bearer <crmKey>`, а не `?key=` в URL (ключ в query утекает в логи — `SEC-7`).
- Где проверяется: [src/lib/wazzup-webhook.ts](../../src/lib/wazzup-webhook.ts) → `isWazzupWebhookAuthorized`; [src/app/api/wazzup/webhook/route.ts](../../src/app/api/wazzup/webhook/route.ts).

### Эксплуатация (следствие P0)
- ⬜ Отмена оплаченного заказа теперь требует **открытой смены** (туда проводится возврат `cash_refund`). Если смена закрыта — отмена не выполнится с понятной ошибкой, деньги не теряются. Учитывать в рабочем процессе кассиров.

## После фазы P1 (производительность + целостность данных)

Кода-изменения, специальных шагов миграции не требуют (индексы создаются автоматически в `migrate()` при старте). Но есть изменения поведения, которые нужно довести до сотрудников:

- ⬜ **Новые индексы** применяются сами при первом старте на существующей `app.db` (через `CREATE INDEX IF NOT EXISTS`). Отдельных действий не нужно; на больших БД первый старт может занять чуть дольше.
- ⬜ **Перепродажа заблокирована для заказов/сделок** (`BL-3`): нельзя создать заказ/сделку на количество больше доступного остатка (`доступно = остаток − резерв`). Касса (быстрая продажа) по-прежнему разрешает уход в минус. Если на складе есть товары с уже отрицательным `available`, новые заказы по ним не создадутся, пока не пополните остаток.
- ⬜ **Импорт склада больше не меняет резерв** (`BL-4`): колонка `reserved` из XLSX игнорируется (резерв ведётся заказами). Остаток применяется как дельта к текущему — если между предпросмотром и применением были продажи, они не затрутся.
- ⬜ **Позиции сделки фиксируются после создания заказа** (`BL-6`): чтобы поменять состав — измените или отмените связанный заказ.
- ⬜ **Удаление товара** блокируется, если есть резерв / товар в активных заказах / в истории продаж (`BL-5`).
- ⬜ **Авто-обновление страниц** теперь происходит только при реальном изменении (новый заказ/смена статуса/оплата, новая входящая сделка), а не каждые 5с (`PERF-2`). Если кто-то правит карточку сделки на другом ПК, страница обновится при следующем изменении счётчика или вручную (F5).
